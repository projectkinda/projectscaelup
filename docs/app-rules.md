# Android Pro app rules

Schedule and shared daily-limit enforcement are implemented without production rule screens. The only UI added is an Android development panel next to the Settings tier switcher. iOS native code, coach code, and session/lockdown formulas were not changed by this task. Existing unrelated workspace edits remain in place.

## Rules and persistence

A rule covers 1-20 distinct eligible package names, independently of flagged apps and their free cap. Up to 10 stored rules are allowed, including deleted rules still retiring today. A schedule selects Monday=1 through Sunday=64 and local start/end minutes. End <= start crosses midnight and belongs to the start weekday; equal times represent a full 24-hour wall-clock window. Production windows are at least 15 minutes. Daily limits are 5-1440 minutes, shared by all apps in that rule as the sum of their foreground milliseconds.

`app_rules` uses the requested columns in `src/data/database.ts`. `retired_json` contains only `{snapshot, enforcedUntil}` entries. Delete sets the current version disabled, retires the old snapshot, and stores a tombstone under `app_rule_deleted:<id>` in the existing `app_state` table. Deleted rules disappear from `listRules` immediately; their rows and tombstones are removed on repository access after retirement expires. Disabled rules remain editable. Snapshot pruning uses conditional SQL so a concurrent reader cannot overwrite a newer edit.

Every update, including a no-op edit, disabling, or deletion, retains the old snapshot until the next local midnight calculated at edit time. All earlier non-expired snapshots remain too. Enforcement is the union of the enabled current version and enabled non-expired retired versions. There is no attempt to classify an edit as tighter/looser. Creating a rule has no retired version. This means a lower budget or new scheduled window applies immediately, while an older, stricter version may continue blocking through tonight.

`appRulesRepository.ts` exposes `listRules`, `createRule`, `updateRule`, `deleteRule`, `getEnforcedVersions`, and `syncRulesToNative`. Mutations serialize in JS and return `{ok, rule}` or `{ok:false, error}` instead of throwing into UI. Writes and deletion tombstones share a SQLite transaction. Sync runs after changes, at app start, whenever the app returns active, and on every `subscribeToTier` change. Sync is serialized and rechecks `isPaidUser()` after asynchronous DB reads. An unpaid sync sends `[]`, which sets native rule enforcement disabled; SQLite rules remain. A paid read failure leaves the previously synced native state intact. Existing post-session lockdowns retain their normal behavior in both tiers. The existing entitlement stub still needs the planned billing integration.

`appRules.ts` holds pure validation, snapshots/retirement, calendar-midnight calculation, and schedule-window preview logic. `appRulesModule.ts` contains safe Android bridge wrappers and `getSelectableRuleApps()`, which returns eligible installed launchable apps without the flagged-app cap, ready for a future `AppPickerList`. No production picker or rule screen was added.

## Native execution

- `AppRuleDenylist` mirrors the TS protected-package constant; fixtures compare them exactly. `AppRulePackages` extends it using installed input methods, home intent handlers, Settings handlers, dial intent/default dialer, and emergency intent handlers. Own package, System UI, keyboards, launchers, Settings, dialer/telecom, and emergency apps cannot contribute rule usage or show a block, even when a stale snapshot contains one. Selection also uses these exclusions. Queries are declared explicitly; no `QUERY_ALL_PACKAGES`, Usage Access, exact-alarm, or window-content permission was added.
- `RuleStore` persists the enforced JSON versions and an enabled flag in SharedPreferences. Only `AppRulesBridge` writes it. Native validation protects durations, apps, weekdays, and package exclusions; release builds also reject short dev durations when reading a persisted debug store. Retired versions expire natively without waiting for JS to run.
- `UsageLedger` stores only a local date key and per-package aggregate foreground milliseconds for limit-covered apps. It does not collect visits, window content, or unrelated app history. Newly covered packages start counting when covered; use before rule creation cannot be reconstructed without collecting unrelated usage. Today totals survive edits and temporary tier changes, so upgrading/re-enabling does not reset today's budget. A local-date change resets the ledger. Nothing accrues while rule enforcement is disabled.
- `BlockEvaluator` has no Android imports. It uses `java.time` local calendar dates in the supplied zone for schedule boundaries and next midnight. It ignores expired versions, caps a retired block at its expiry, sums each version's distinct apps, and selects the latest ending block including the existing `LockdownStore` expiry. Java time is desugared for the app's Android 7 minimum.
- `RuleForegroundTracker` lives with the accessibility service. Window changes close the previous foreground segment. Eligible, usable foreground apps open a new segment; blocked time does not accrue. A handler persists progress at most every 30 seconds and schedules earlier wakeups for remaining shared budget, schedule starts/ends, retirement expiry, and midnight. `elapsedRealtime` caps duration to avoid counting forward wall-clock jumps as usage. Screen-off closes the segment and cancels timers. Time/timezone changes trigger re-evaluation. Service reconnect cleans up old receivers and callbacks.
- A blocked open reports our own package to the existing JS/away trackers, cancelling the visit rather than recording a distraction. The same cancellation happens when a rule starts mid-use. Real usable foreground time before the block retains the existing distraction thresholds; their formulas were not changed.
- `LockdownOverlayService` evaluates the combined block. It keeps the existing full-screen dark/rust appearance, with no override. LOCKDOWN text stays `Locked` / `N min remaining`. SCHEDULE is `Blocked` / `Until h:mm am/pm` / `Your schedule`. LIMIT is `Daily limit reached` / `Back tomorrow` / e.g. `1h 30m per day`. Expiry/tier changes refresh an already-visible overlay. A foreground transition away or screen-off cancels a pending show, including the race before the service finishes starting. The service can start for rules alone and stays alive while lockdowns or enforced rule versions can require it; expired rule-only state is swept every 30 seconds.

## Screen-on resume and other limits

[Android's accessibility window API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#getWindows()) requires window-content capability plus the interactive-windows flag. This app deliberately retains `canRetrieveWindowContent=false`. `ACTION_USER_PRESENT` indicates unlock but supplies no foreground package, and a cached pre-lock package is not reliable if unlock launches another app. No reliable package lookup was established without extra access. We therefore wait for a real window-state event after screen-off/reconnect. If the same app resumes without one, usage undercounts and an overdue rule overlay may be delayed until that event. The foreground app is not guessed, avoiding a stale block over a protected app. This behavior needs handset testing.

Accessibility must be enabled and overlay permission granted. When either is unavailable, blocking is not guaranteed. Turning the accessibility service off closes accounting, cancels rule callbacks, and hides the current overlay; stored rules remain for reconnection. Clearing app data removes rules, ledger, and enforcement. Android force-stop/OEM process killing can prevent service restart and enforcement until the app/accessibility service runs again. Rules and persisted totals survive an ordinary process restart/reboot, but the OS must reconnect accessibility; we added no boot receiver or exact alarm. An unflushed open segment is lost on abrupt death (normally up to 30 seconds); time while the service is absent is not inferred. No claim of bypass-proof device management is made.

Schedules follow the device's current timezone and local weekdays. Normal daily rollover compares local-date keys; DST midnights can be 23 or 25 hours apart. Java resolves nonexistent DST local times forward and ambiguous times to the earlier offset; both ends use the same convention. Retirement ISO timestamps are fixed at the next local midnight as calculated when edited, so timezone changes do not extend/rebase an already recorded retirement instant. Changing timezone across a date boundary resets today's ledger; changing the clock/date can cause resets or conservative undercount. Multi-window/PiP is based on the last window-state package and is not proven on device. The implementation is a foreground blocker, not a device-owner policy.

## Development panel

Use an Android debug/development build, `DEV_FLAGS.tierSwitcher=true`, the Paid override, accessibility enabled, and overlay permission granted. Under Settings > Subscription:

1. **Add 3-min schedule block for my first flagged app (starts now)** adds a local three-minute window covering the current calendar minute on today's weekday. Because rules store whole minutes, its remaining duration is between two and three minutes.
2. **Add 1-min daily limit for my first flagged app** adds a shared one-minute rule. A pre-existing total for that package counts; clear app data on a disposable test install if a fresh usage total is necessary. The reset button deliberately preserves today's usage.
3. **Show today's usage for rule apps** prints native aggregate milliseconds for limit-covered rule packages. Schedule-only apps are intentionally not tracked.
4. **Clear all rules** immediately deletes test rows/tombstones and syncs empty enforcement. This explicit development reset bypasses retirement. It is not a production delete API.

An additional dev-only **Add 3-min schedule starting in 1 min (mid-use test)** button lets you add a window, switch into the target app before the next local minute, and test a scheduled block without a debugger. This is the only addition to the four requested test buttons.

The 3/1-minute fixture writer bypasses only production duration minimums, after validating apps/weekdays/shape. It is gated by `__DEV__` and `DEV_FLAGS.tierSwitcher`; native short durations require a debuggable APK. The panel, action text, dynamic test imports, and reset action are absent/inert in release compilation even if someone leaves the tier flag on. Set the flag false before release anyway.

The test panel uses the first flagged app only for convenience; production rule storage and the selection helper are independent of the flagged-app list.

## Automated checks

- `npx tsc --noEmit`.
- `npx tsx scripts/app-rules-check.ts`: 17 grouped JS checks using the real schema and repository against isolated SQLite. Includes DST/year boundaries, create/edit/double-edit/disable/delete, expired-row cleanup, bounds, midnight windows, cross-language denylist parity, unflagged apps, concurrent rule cap, tier changes, failures, non-Android no-ops, and release panel stripping.
- `android/gradlew.bat -p android :app:testDebugUnitTest --offline --console=plain`: Kotlin/Java app compilation and 12 JVM evaluator tests. Includes schedules inside/outside/end-exclusive, start-weekday overnight, full-day windows, shared budget under/at/over, retirement at midnight, later-end arbitration with lockdown, unpaid rule disabling, protected packages, mid-use timer deadlines, DST, and display formatting.
- Existing History, coach, live timer, and typography fixtures should remain green after the shared schema/startup integration.

No handset or emulator was used. Not verified: actual accessibility event delivery, keyboard/launcher/emergency discovery on OEM devices, mid-use handler/overlay latency, denied/revoked overlay permission behavior, real persisted ledger totals after screen off/unlock, midnight/timezone changes, service/process death, reboot, force-stop, the visible overlay texts/stacking, or real-phone tier transitions. JVM tests do not simulate Android service/WindowManager lifecycle.

- [ ] Use a debug build; enable accessibility and draw-over-other-apps; choose Paid. Verify the dev panel is absent in a release build.
- [ ] Use the additional future-start test button. Open its target before the next minute and remain inside: `Blocked` appears at the start without another app/window event. The immediate three-minute button separately checks rule-only service startup and overlay style.
- [ ] Add the one-minute fixture, remain inside the app, and verify `Daily limit reached` appears mid-use. With a two-app limit, divide use across apps and confirm one shared budget.
- [ ] Screen off/on while using a rule app, including unlock back into the same app with no navigation. Observe the documented no-window-event undercount/delayed enforcement, then navigate away/back and confirm counting/enforcement resumes.
- [ ] Reboot; unlock; verify rules/today's persisted aggregate survive, accessibility reconnects, and the next eligible window event blocks. Record any Samsung battery/autostart restriction.
- [ ] Kill the app process during use; compare saved usage before/after restart (up to the open 30-second segment may be lost). Separately force-stop; confirm the documented enforcement gap until restart.
- [ ] Create a normal 5-minute rule, exhaust it, then loosen to 30 minutes or remove an app using `updateRule`; the previous version must still block today. Verify disable/delete/double-edit preserve every enabled old snapshot. At the recorded midnight, only the new current enabled version remains. The dev reset is not a valid delete test.
- [ ] Switch to Free while blocked: the rule overlay disappears and app rules stop counting/blocking; stored rules remain. Switch back to Paid and confirm today's existing usage and rules return. An independent post-session lockdown may still apply.
- [ ] Overlap a schedule/limit with a real post-session lockdown and verify the reason with the later expiry wins and updates correctly when it expires.
- [ ] Check own app, launcher, Settings, System UI, all installed keyboards, dialer, and emergency flow cannot be rule-selected/counted/blocked. Do not place test emergency calls.
- [ ] Deny/revoke/regrant overlay permission on both Samsung and Pixel; test accessibility off/on, midnight, DST/timezone travel, and multi-window/PiP.
